## The plugin API that actually exists on OpenCode 2.0.24

The spec's research section cited community sidebar plugins, but those use the **v1 API**
(`@opencode-ai/plugin` 1.x: `TuiPluginModule.tui(api)`, `api.slots.register({sidebar_content})`, `api.kv`) which
**does not exist in 2.0.24** — none of those identifiers appear in the installed host. Do not copy v1 examples.

OpenCode 2.0.x has a dedicated **TUI-plugin runtime**, from `@opencode/plugin/tui` (npm package `@opencode/plugin`,
versioned with the host):

- A plugin is `define({ id, setup(ctx) })` — or, equivalently, a default-exported `{ id, setup }` object (the form
  the T391 hooks plugin already ships, proven to load).
- `ctx.ui.slot({ append | prepend | before | after | replace: <path>, render })` claims a place in the host's slot
  tree. Documented slot paths (`dist/tui/context.d.ts` in `@opencode/plugin@2.0.24`): `app`, `home.footer`,
  `home.footer.status`, `prompt.footer`, `prompt.footer.status`, `prompt.footer.file`, `session.composer.top`,
  `session.panel`, **`sidebar.content`** (input: `{ sessionID }`), `sidebar.footer`. Slot paths are documented API
  and stay stable across host refactors; a claim aimed at a removed path degrades to the nearest surviving ancestor.
- Slot `render` returns **Solid JSX** (`@opentui/solid`), reactively: reads of `ctx.storage.memory(...)` stores and
  other reactive getters re-run the render.
- Also available: `ctx.ui.router.register/navigate` (full plugin pages), `ctx.ui.panel.open()` (session side panel),
  `ctx.ui.dialog/toast`, `ctx.keymap.layer(...)`, `ctx.tabs`, `ctx.data.on/listen` (server event stream,
  `OpenCodeEvent` map) plus reactive session stores, `ctx.storage.store/memory`.
- Rendering JSX **without a build step**: JSX is just the `jsx(type, props)` factory from
  `@opentui/solid/jsx-runtime`. A plugin module can call that factory directly and stay plain TypeScript — no `.tsx`,
  no compile step — which is what `src/opencode-sidebar.ts` generates. Whether a loose file in
  `~/.config/opencode/plugins/` can *resolve* that bare import at runtime is host-loader behavior; the plugin loads
  it dynamically with a null fallback (renders nothing rather than failing the host), and a properly packaged npm
  plugin with `@opentui/solid` in its dependencies is the fallback deployment shape.

## The deployment shape that actually reaches the TUI (proven on 2.0.24)

Empirical result from the scratch repro (context-key dumps at `setup()`):

- A **loose file** in `plugins/` loaded via `tui.json` runs with the **server context**:
  `{app, location, options, agent, command, event, generate, model, provider, integration, mcp,
  permission, plugin, reference, rpc, session, shell, skill, storage: {get,set,remove,scan}, tool,
  vcs, websearch, worktree, ...}` — **no `ui`, no `data`, no `storage.store/memory`**. Any `ctx.ui.slot`
  call throws and the plugin is marked failed (the TUI shows "Plugin failed: <id>").
- A **packaged plugin** — a directory whose `package.json` declares separate entrypoints:
  `"opencode": { "server": "./server.ts", "tui": "./tui.ts" }` — is loaded in **both** runtimes. The
  server entrypoint gets the server context; the **tui entrypoint gets the full TUI context**:
  `{options, location, app, renderer, client, data, attention, theme, themeMode, markdown, keymap,
  storage: {store,memory}, ui: {dialog, toast, format, router, panel, tabs, model, slot}}` — matching
  the `@opencode/plugin` npm types. The v1 community examples (`TuiPluginModule.tui(api)`,
  `api.slots.register`) do not exist in 2.0.24; do not copy them.
- So the shipped shape is a **package directory** (three files, generated by `src/opencode-sidebar.ts`:
  `package.json`, `server.ts` no-op, `tui.ts` the sidebar). `agentmbx setup` wiring (T411) should
  install that directory, not a loose file.

## Refresh mechanism and its cost

- The slot input carries the active `sessionID`; the plugin fetches
  `GET http://127.0.0.1:<MBX_PORT|7373>/v1/status?cli=<MBX_STATUS_CLI|opencode>&session=<sessionID>&schema=mbx.status/v2`
  (the T407 loopback endpoint) when the session changes and, while a session is bound, at most once per 5 s.
- A 1 s interval only compares timestamps (`sessionID` set? snapshot older than 5 s?); it issues **no** requests by
  itself and its cost while the sidebar is away is one `Date.now()` comparison per second. Each actual fetch is one
  loopback HTTP GET (~1 KB response) and costs the daemon one v2 snapshot computation — the same queries the HUD
  writer and statusline adapters already serve (`src/hud.ts`), no new store load. Worst case with the TUI left open:
  ~12 requests/minute to a loopback socket.
- Reactive updates: the fetch resolves into a `ctx.storage.memory` Solid store, so the render re-runs only when a
  snapshot actually changes (and Solid diffs the JSX).

## Read-only contract

The plugin contains zero status logic: `formatStatusV2` maps a v2 snapshot to one line
(`mbx <identity> N↑ N↺ owner:N [lease-unverified]`) and degrades to `mbx ?` when the daemon is unreachable — it
never throws inside the host. It never reads the store, never resolves identities, never derives anything: one
producer (the daemon, T404/T405), N renderers.

## Live scratch repro (what was and wasn't proven)

Environment: `MBX_HOME=/tmp/mbx-t409` and `OPENCODE_CONFIG_DIR=/tmp/oc-t409`, a scratch agentmbx daemon
on a non-default port serving the v2 endpoint (run from the T404 branch build), the generated plugin
packaged into the scratch plugins directory and registered in the scratch `tui.json`. The owner's
`~/.config/opencode` was never written to.

- Proven live: the packaged plugin loads on OpenCode 2.0.24 in **both** runtimes with no load error;
  the TUI entrypoint receives the real TUI context (`ui.slot` present); the v2 endpoint answers the
  scratch session with live identity and counts.
- Proven in harness tests (6/6): the slot claim targets `sidebar.content`, the fetch URL is the T407
  contract, `formatStatusV2` renders the Claude mod fixtures line-for-line, and the render shows
  exactly what the daemon sent.
- NOT proven when work was paused (owner-side OpenCode crash report; all OpenCode activity stopped by
  the lead's order and the scratch isn't isolated enough to continue): the visual render inside a live
  TUI session, and an actual observed fetch crossing the wire (the scratch never had a session in the
  sidebar when the runs stopped). Deferred to T410, together with a fully isolated repro (the scratch
  shared `~/.local/share/opencode` state with the owner's install — that coupling is recorded as a
  lesson: `OPENCODE_CONFIG_DIR` alone does not isolate OpenCode's state/log directories).

## Risks and open questions for T410/T411

1. The packaged-plugin layout is required; setup wiring (T411) must install a directory (package.json
   + two entrypoints), and doctor should verify the entrypoints load in both runtimes.
2. `@opentui/solid/jsx-runtime` is loaded dynamically with a null fallback; on the packaged TUI path it
   should resolve (packaged plugins share the host's module resolution), but T410 should assert the
   rendered element visually once.
3. `sidebar.content` renders beside other plugins' claims in enable order; `replace` is available if
   the full sidebar (T410) wants the whole boundary.
4. The 5 s refresh constant is a spike choice; T410 should re-evaluate against `ctx.data.on` session
   events as additional triggers (cheaper when idle, immediate on activity).
